# ЗАДАЧА 003: Универсальные скрипты синхронизации с GitHub github_download и github_upload файлы

**Дата:** 2026-05-24
**Статус:** Реализовано
**Цель:** Два маленьких автономных bash-скрипта (`github_upload.sh` и `github_download.sh`), которые можно положить в любой git-репозиторий и пользоваться без правок.
**Универсальность проектов** : Подходит для всех проектов, просто скопировать github_download и github_upload файлы в любой проект ,в котормо есть подключенынй .git папка и щсташп внутри него
---

## Краткое резюме

В корне репозитория появились два исполняемых файла:

| Файл | Назначение |
|------|-----------|
| `github_upload.sh` | Анализирует локальные изменения, для **каждого** изменённого файла создаёт отдельный короткий коммит (до 500 символов) с автоматически сгенерированным описанием, затем выполняет `git push`. |
| `github_download.sh` | Подтягивает последние изменения с remote (`git fetch` + `git pull --rebase`). Если есть незакоммиченные правки — прячет их в `stash` и возвращает после. |

Оба скрипта **универсальны**: они не содержат имени аккаунта или репозитория. Все нужные параметры берутся из стандартного `.git/config`:

- текущая ветка — `git rev-parse --abbrev-ref HEAD`
- удалённый репозиторий — `git config branch.<branch>.remote` (по умолчанию `origin`)

Скрипты можно просто скопировать в любой другой проект и пользоваться без модификаций.

---

## github_download.sh

### Что делает (по шагам)

1. Проверяет, что текущая папка — git-репозиторий, переходит в его корень.
2. Определяет текущую ветку и её remote.
3. Если в рабочей копии есть несохранённые правки или untracked-файлы — прячет их через `git stash push -u` с пометкой времени.
4. Делает `git pull --rebase <remote> <branch>` — это тянет последние изменения и переустанавливает локальные коммиты поверх удалённых (без merge-коммитов).
5. Возвращает спрятанные изменения через `git stash pop`.
   - Если возникает конфликт при pop — скрипт сообщает об этом и завершает работу с ошибкой; разбираться вручную (`git status`).

### Как запустить

```bash
./github_download.sh
```

### Возможные ошибки и поведение

- **Не git-репозиторий** → `set -e` обрывает выполнение, печатается осмысленное сообщение.
- **Нет remote для ветки** → используется `origin` как fallback.
- **Конфликт при `stash pop`** → не пытается ничего перезаписывать, оставляет состояние пользователю.

## github_upload.sh

Это основной скрипт. Его задача — **не просто `git add . && git push`**, а сгенерировать осмысленное короткое сообщение коммита для каждого изменённого файла на основе анализа diff. Никаких ИИ-моделей не используется — это чистый разбор текста diff.

### Что делает (по шагам)

1. Проверяет git-репозиторий, переходит в корень, определяет ветку и remote.
2. Делает `git fetch` без вмешательства в локальные коммиты (чтобы знать актуальное состояние remote).
3. Получает список изменений через `git status --porcelain=v1 -z` (null-terminated — корректно работает с именами файлов, содержащими пробелы и спецсимволы).
4. Для каждого файла вызывает `generate_message()`, который собирает короткое описание (см. ниже).
5. Формирует полное сообщение коммита: `<имя_файла>: <описание>`.
6. Обрезает его до **500 символов** через `truncate_msg()` (считается по символам, не по байтам — корректно работает с UTF-8 / кириллицей).
7. Стейджит **только этот один файл** (`git add -A -- <file>`) и делает на него отдельный коммит.
8. После обработки всех файлов делает один `git push`.

### Логика `generate_message()` — как пишутся сообщения

В зависимости от статуса файла из `git status`:

| Статус | Сообщение |
|--------|-----------|
| `??`, `A`, `AM`, `MA` (новый файл) | `новый файл (N строк)` — где N считается через `wc -l`. |
| `D`, `AD` (удалён) | `файл удалён` |
| `R`, `RM` (переименован) | `файл переименован` |
| Любая модификация (`M`, ` M`, `MM`, …) | Полный анализ diff (см. ниже) |

#### Анализ diff для модифицированных файлов

Из вывода `git diff HEAD -- <file>` извлекаются 4 показателя:

1. **Количество добавленных и удалённых строк** — простой подсчёт через `grep -c '^+[^+]'` и `grep -c '^-[^-]'` (исключая заголовки `+++ ` / `--- `).

2. **Контекст функций** — git в заголовках hunks (`@@ -10,5 +10,7 @@ def foo():`) после второго `@@` показывает функцию, в которой произошли изменения. Скрипт берёт текст после второго `@@`, обрезает по `(`, `{`, `:`, `=`, убирает префиксы вроде `def`/`class`/`function`/`fn`/`func`/`async def`/`public`/`private`/`static` и оставляет голые имена.

3. **Добавленные определения** — строки, начинающиеся с `+` и содержащие `def `/`class `/`async def `/`function `/`fn `/`func `/`public `/`private `/`static `. От имени остаётся только идентификатор.

4. **Удалённые определения** — то же самое для строк с `-`.

Все четыре списка дедуплицируются (`sort -u`), ограничиваются 5 элементами, и через `paste -sd ,` склеиваются в `foo, bar, baz`.

#### Итоговое сообщение

```
<имя_файла>: изменения (+<N>/-<M>); затронуты: <funcs>; добавлено: <added>; удалено: <removed>
```

Пустые секции опускаются. Пример реального вывода тестового парсинга:

```
sample.py: изменения (+3/-3); затронуты: foo; добавлено: baz; удалено: bar
```

Это означает: в `sample.py` добавлено 3 строки и удалено 3, изменения произошли внутри функции `foo`, появилась новая функция `baz`, исчезла функция `bar`.

#### Поддерживаемые языки

Парсинг сделан универсально через ключевые слова `def`/`class`/`function`/`fn`/`func`/`async def`/`public`/`private`/`static`, так что корректно распознаёт изменения в:

- **Python** (`def`, `class`, `async def`)
- **JavaScript / TypeScript** (`function`, `class`)
- **Rust** (`fn`)
- **Go** (`func`)
- **Java / C# / C++** (`public`, `private`, `static`)

Для других языков сообщение всё равно сформируется — просто без блока «затронуты / добавлено / удалено», а только со счётчиком `+N/-M`.

### Обрезка до 500 символов

Функция `truncate_msg()`:
- считает длину через `wc -m` (символы, не байты — важно для кириллицы),
- если длина превышает лимит — обрезает и добавляет `…`.

Это гарантирует выполнение требования из ТЗ: «не больше 500 символов на файл».

### Обработка особых случаев

- **Файлы с пробелами / спецсимволами в именах** — корректно работают благодаря `git status --porcelain=v1 -z` (null-terminator) и `mapfile -d ''`.
- **Переименования / копии** — git в режиме `-z` выдаёт две записи подряд (новое имя, потом старое). Скрипт пропускает старое имя из следующей записи, чтобы не споткнуться.
- **Файлы без реальных изменений после `git add`** — пропускаются (за исключением чистых переименований без модификаций — они коммитятся).
- **Нет изменений вообще** — печатает «Нет изменений для отправки» и выходит с кодом 0.

### Как запустить

```bash
./github_upload.sh
```

## Установка в другой репозиторий

1. Скопировать оба файла в корень нужного репозитория:
   ```bash
   cp github_upload.sh github_download.sh /path/to/other/repo/
   ```
2. Выставить права на исполнение (если потерялись):
   ```bash
   chmod +x /path/to/other/repo/github_upload.sh /path/to/other/repo/github_download.sh
   ```
3. Готово — никаких правок внутри скриптов делать не нужно. Аккаунт, имя репозитория и текущая ветка определяются автоматически из `.git`.

> **Авторизация** должна быть уже настроена (SSH-ключ или сохранённый `gh auth` / `https`-токен). Скрипты не лезут в учётные данные — этим занимается сам `git push`/`git pull`.

## Что не используется (намеренно)

- **ИИ-модели / LLM** — не нужны. Текстовый анализ diff покрывает требование «коротко описать, что изменилось».
- **Никаких внешних зависимостей** — только `bash`, `git`, `awk`, `sed`, `grep`, `wc`, `paste`. Всё это есть в любом Linux/macOS из коробки.
- **GitHub API / `gh` CLI** — не нужны, скрипты общаются с GitHub через обычный `git push`/`git pull`.

## Ограничения и возможные улучшения в будущем

- Длинные diff'ы по одному файлу всё равно даюют короткое сообщение — это by design (требование ≤500 символов). При желании лимит можно поднять, изменив второй аргумент в `truncate_msg`.
- Распознавание функций — эвристическое. Не ловит, например, методы внутри классов на Ruby (`def`), стрелочные функции JS без ключевого слова, или нестандартные конструкции на DSL.
- Если в одном коммите хочется объединить несколько связанных файлов (например, рефактор) — текущий скрипт всё равно сделает отдельный коммит на каждый. Это можно расширить ключом `--group`, но в текущей задаче не требуется.
